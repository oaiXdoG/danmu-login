# 登录票据规则

## 1. 定义

`loginTicket` 是登录服生成、客户端转发、游戏服解密的登录凭证。加密服务处理的是完整 JSON 字符串，不感知 JSON 内的业务字段。

当前规则：

- 不使用 JWT。
- 不使用 MD5 参数签名。
- 不把票据写入登录服 Redis。
- 当前登录调用传入的 JSON 包含 `userId` 和 `anchorOpenId`，票据协议本身不固定业务字段。
- 使用 AES-GCM 提供保密性和篡改检测。

## 2. 明文内容

当前登录业务传入的 JSON 示例为：

```json
{
  "userId": 10001,
  "anchorOpenId": "主播唯一标识"
}
```

`userId` 是登录用户数据库 ID，`anchorOpenId` 是对应的主播身份标识。本地测试登录时，`anchorOpenId` 使用用户数据库 ID 的字符串值；抖音登录时，使用抖音直播信息返回的主播身份标识。业务层负责组装和解析 JSON。`LoginTicketService` 不解析、不修改 JSON，只负责对完整字符串进行加密和解密。客户端不得额外提交字段覆盖解密后的内容。

后续增加业务字段时，只扩展这段 JSON；加密和解密协议不变。

## 3. 密钥

配置项为：

```properties
ticket-key=<Base64 编码的 AES 密钥>
```

登录服和目标游戏服配置同一把密钥，客户端不持有密钥。配置值先进行 Base64 解码，再作为 AES 密钥使用；当前要求解码后为 32 字节。

## 4. 加密结果

算法：

```text
AES/GCM/NoPadding
```

每次加密生成一个新的 12 字节随机 IV。AES-GCM 生成 16 字节认证 Tag，Tag 随密文一起传输，不是固定业务字段。

最终二进制布局：

```text
IV（12 字节） + 密文 + Tag（16 字节）
```

整个二进制结果使用 Base64 URL 安全编码且不带 `=` 填充，编码后的字符串就是 `loginTicket`。

## 5. 解密与篡改检测

游戏服收到 `loginTicket` 后：

1. 使用 Base64 URL 解码。
2. 取前 12 字节作为 IV。
3. 将剩余内容作为密文和认证 Tag。
4. 使用相同密钥执行 AES-GCM 解密。
5. Tag 校验成功后返回原始 JSON 字符串，由业务层解析其中的字段。

以下情况必须拒绝票据：

- Base64 格式错误。
- 票据长度不足。
- 密钥不匹配。
- 密文或 Tag 被修改。
AES-GCM 的 Tag 不是一个固定值，也不是拿来和固定字符串比较的业务字段。它由密钥、IV 和密文共同计算；密文任意内容被修改都会导致校验失败。

解密服务返回原始 JSON 字符串，业务层负责解析；业务层解析失败时必须拒绝登录。

## 6. 当前未实现的规则

当前登录票据和统一登录响应都没有过期时间字段，因此游戏服不能仅凭 `loginTicket` 独立判断过期。

当前没有一次性消费机制，同一张未被其他机制拒绝的票据可以重复提交。后续若需要过期或防重放，应先单独确定字段和存储边界，再修改协议。
